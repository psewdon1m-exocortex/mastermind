# Mastermind — context-indexing, Curator и интеграция Crusher

Версия: **1.0 — итоговая спецификация для реализации**. Дата: **2026-09-19**.

Собственное обозначение общего механизма: **context-indexing**. Python namespace: `context_indexing`; настройки и внутренние контракты используют это же обозначение. Название файла сохранено для совместимости существующих ссылок.

Статус: целевое поведение согласовано в обсуждении; этот документ задаёт контракт будущей реализации, а не подтверждает её наличие или прохождение тестов. Реализация поставляется одним согласованным пакетом с внутренними этапами и проверками.

## 2. Принятые решения

| ID | Решение |
| --- | --- |
| D01 | Сохраняется структура Query Processor → Retriever → Candidate Set → Fusion → Reranker → Relation Expansion → Path Consistency Check → Confidence Evaluator → опциональный Curator/повторный поиск → результат. |
| D02 | Общий поиск не ограничивается нотами с `#main`/`#key`; обычные заметки и их фрагменты являются полноценными результатами. |
| D03 | Ограничение допустимых опорных нот принадлежит политике Crusher. Найденная заметка не становится автоматически разрешённой опорой. |
| D04 | Все новые файлы, созданные Crusher, сохраняются в `root/crusher`, независимо от выбранного места в графе и применения fallback. |
| D05 | Ссылку на выбранную опорную ноту содержит новая заметка. На каждом запуске Crusher опорная нота не переписывается. |
| D06 | Резервное место в графе — нота `pool`, по умолчанию связанная с настроенной корневой нотой как `root → pool`. Это не резервная папка файлов. |
| D07 | Путь к резервной ноте настраивается в Mastermind. Default: `root/pool.md`, с учётом уже существующей ноты `pool` при миграции. |
| D08 | Crusher создаёт содержимое по выбранному Markdown-шаблону. Default: `root/templates/example crusher.md`. |
| D09 | Путь к шаблону редактируется в Settings рядом с выбором резервной ноты. Шаблон является обычным файлом canonical Vault и редактируется в Obsidian. |
| D10 | Настройки Obsidian и поискового пайплайна пока объединены в одну карточку `Obsidian & search`. |
| D11 | В этой же карточке находится переключатель `Enable Curator` и его фактическая готовность. Curator опционален и не вызывается для каждого запроса. |
| D12 | Curator формирует проверяемую поисковую гипотезу; он не пишет в Vault и не назначает себе право принять placement. Разрешён максимум один дополнительный проход. |
| D13 | Общий поиск, embeddings и Curator работают локально. Внешние understanding/generation идут через принятую границу Wyvern; полного экспорта базы в модель нет. |
| D14 | Файлы не перезаписываются, запись выполняется через canonical coordinator/journal с проверкой актуальности и идемпотентностью. |
| D15 | Внедрение — один функциональный пакет с отдельными внутренними проверками. Полноценная аналитическая система и сложная онтология в него не входят. |
| D16 | Все проверки выполняются на основном диске; обязательных восьмичасовых прогонов, переноса базы и тестовых передач 8 GiB нет. |

## 3. Термины и независимость двух структур

- **Vault-relative path** — нормализованный путь относительно корня canonical Vault. `root/crusher` не означает абсолютный каталог `/root` Linux или корень диска Windows.
- **Корневая нота графа** — нота, выбранная существующей настройкой `crusher_root`; её текущий default — `root.md`. Имя каталога `root/` не определяет местоположение этой ноты.
- **Evidence** — найденная заметка, её фрагмент, подтверждённая ссылка, metadata или профиль с указанием происхождения.
- **Placement target / anchor** — нота, которую политика Crusher разрешила использовать как опору новой заметки.
- **Fallback anchor** — явно выбранная резервная нота, обычно `pool`.
- **PlacementProfile** — производное описание структурной ветки, не новая авторитетная заметка и не пересказ, принимаемый за факт.
- **Curator** — локальный помощник уточнения поиска, изолированный от mutation.

Пример нормального результата:

```text
Файл:       root/crusher/Обработка больших файлов.md
Связь:      новая заметка → [[Загрузка файлов]]
Положение:  root → Projects (#main) → Saturn (#key) → Загрузка файлов (#key)
```

Пример результата при недостатке уверенности:

```text
Файл:       root/crusher/Обработка больших файлов.md
Связь:      новая заметка → [[pool]]
Положение:  root → pool
```

Различаются только выбранная графовая связь и причина решения. Папка нового файла в обоих случаях одна. Новые generated notes не получают `#main`/`#key` автоматически.

## 4. Границы модулей и основной поток

```text
Потребитель: Query + Subject + Scope + Policy
                      |
                Query Processor
                      |
     raw text / entities / metadata / filters
                      |
            локальные поисковые каналы
  FTS/BM25 | Vector | Entity | Metadata | Graph | Temporal
                      |
                 Candidate Set
                      |
          Exact Deduplication + Fusion
                      |
                   Reranker
                      |
              Relation Expansion
                      |
      оценка расширенного набора тем же Reranker
                      |
             Path Consistency Check
                      |
              Confidence Evaluator
                 /             \
         достаточно        нужна дополнительная проверка
               |             Curator, если разрешён и готов
               |                  |
               |          проверенный Proposal
               |                  |
               |        один повторный проход:
               |        retrieval → fusion → ranking →
               |        expansion → consistency → confidence
                \                 /
                 RetrievalResult
                      |
           политика конкретного потребителя
```

Для Crusher политика подключает Structural Target Index и PlacementProfile как дополнительное представление/оценку результатов. Eligibility не ограничивает общий Evidence Set: программа сначала собирает свидетельства, затем агрегирует их в пользу допустимых опор. Placement confidence вычисляется по агрегированным опорам, а не по рейтингу случайной обычной заметки.

`Path Consistency Check` в общем механизме проверяет существование, направление, версии и provenance использованных связей. Только адаптер Crusher добавляет требования `root/#main/#key`. Циклы в обычном графе допустимы и обрабатываются visited-set; они не запрещают общий поиск.

Общий результат не содержит команды записи или обязательного поля `placement`. Crusher преобразует его в `PlacementDecision`, затем формирует и записывает заметку. Другой потребитель может использовать тот же результат без этого преобразования.

### 4.1. Минимальные интерфейсы

```text
QueryProcessor.build(query, subject, scope, policy, settings_snapshot) → QueryPlan
Retriever.retrieve(plan, snapshot) → EvidenceCandidate[]
Fusion.combine(candidates, config) → EvidenceCandidate[]
Reranker.rank(candidates, plan, policy) → RankedSet
RelationExpansion.expand(ranked, plan, snapshot) → EvidenceCandidate[]
ConsistencyChecker.check(ranked, snapshot, policy) → CheckedSet
ConfidenceEvaluator.evaluate(checked, policy, calibration) → Assessment
Curator.assist(bounded_context) → CuratorProposal
RetrievalPipeline.run(...) → RetrievalResult
CrusherPlacementPolicy.decide(result, target_index, fallback) → PlacementDecision
TemplateRenderer.render(template_snapshot, generated_fields, trusted_fields) → Markdown
CrusherCommit.apply(validated_note, decision, expected_versions) → CommitReceipt
```

Разделение интерфейсов не требует отдельных микросервисов. Оркестрация, политика и запись остаются в Core, тяжёлые локальные операции — в ограниченном Worker. Вызовы Curator и provider не выполняются внутри filesystem/DB critical section.

## 5. Данные, идентичность и контракты результатов

### 5.1. QueryPlan

Обязательные поля: `query_id`, `schema_version`, `query_type`, `subject`, `scope`, `strategies`, `filters`, `limits`, `policy_id`, `policy_version`, `settings_revision`, `snapshot_id`.

- `query_type`: в пакете реализуются `knowledge_lookup` и `placement_analysis`. Остальные типы резервируются без имитации поддержки.
- `subject`: текст запроса, bounded raw source chunks, title/summary/topics, подтверждённые entity mentions и metadata; нет полного Vault.
- `scope`: principal и разрешённые пространства/объекты. Вычисляется сервером, а не принимается от Curator или гостя.
- `filters`: разделяются на жёсткие ограничения доступа и мягкие поисковые признаки. Curator может уточнять только мягкие признаки.
- `limits`: общий бюджет обоих проходов и отдельные лимиты стадий.
- Запрос Crusher исполняется внутренним service principal. Public submitter получает только свой receipt/progress и не приобретает право вызвать общий поиск.

### 5.2. EvidenceCandidate

```text
candidate_id, kind: note | chunk | entity | relation | profile
source_ref: {vault_id, path, source_sha256}
chunk_ref?: {ordinal, start, end, chunker_version}
strategies: [{name, rank, raw_score, index_generation}]
matched_terms, matched_entity_refs, evidence_refs
graph_paths?: [{nodes, edges, source_versions}]
features, provenance, access_scope
```

В первой версии идентичность чтения строится на `vault + path + hash`; постоянный новый UUID внутри каждого Markdown не требуется. Rename/move и delete/recreate инвалидируют старые ссылки индекса. Сопоставлять разные версии только по одинаковому имени нельзя. Известный подтверждённый rename может использовать существующую историю ссылок, но перед действием проверяется актуальный путь и hash.

### 5.3. Общий результат

`RetrievalResult` содержит `query_id`, `status`, ранжированные объекты, evidence, проверенные пути, признаки оценки, диагностические причины, использованные версии и сведения о Curator.

`status`: `sufficient`, `ambiguous`, `insufficient_evidence`, `unavailable`. Отдельные поля `degraded`, `missing_strategies`, `truncated`, `stale_evidence` описывают неполноту. Числовая вероятность допускается только при наличии применимой калибровки; иначе передаются score/features и категория уверенности.

`curator`: `requested`, `effective`, `invoked`, `reason`, `outcome`, `model_digest`, `passes`. `outcome` различает `not_needed`, `disabled`, `unavailable`, `timeout`, `interrupted`, `invalid_proposal`, `no_improvement`, `refined`.

### 5.4. Решение Crusher

```text
PlacementDecision
  outcome: placed | pooled | blocked_configuration
  anchor_ref: {path, sha256} | null
  structural_path: NoteRef[]
  output_directory: root/crusher
  evidence_refs, reason_codes
  policy_version, calibration_version
  hierarchy_generation, evidence_generation, profile_generation
  settings_revision, template_sha256
```

`pooled` — успешное безопасное размещение при неопределённости, не ошибка job. `blocked_configuration` — невозможность выполнить обязательные условия записи, например отсутствие пригодного pool или шаблона; завершённой заметки в этом состоянии нет.

## 6. Индексы, поиск и профили веток

### 6.1. Обязательные каналы пакета

| Канал | Реализация первого пакета | Ограничение |
| --- | --- | --- |
| FTS/BM25 | Существующий SQLite FTS по заметкам/фрагментам, title и metadata; дополнительный индекс профилей Crusher | Пустой результат FTS не отключает vector search |
| Vector | Независимый поиск по существующему локальному chunk index; отдельные embeddings профилей | Не только rerank FTS-кандидатов; версии моделей не смешиваются |
| Entity | Совпадения явно подтверждённых имён и aliases с provenance; строки understanding используются как запросы | Нет выдуманного canonical ID и автоматического слияния одноимённых людей |
| Metadata | Проверенные tags, type, path, известные поля frontmatter | Папка хранения Crusher сама по себе не определяет тему |
| Graph | Существующие разрешённые внутренние ссылки и обратные ссылки, bounded traversal | Обычная ссылка не становится `discussed_with` или другой семантической relation |
| Temporal | Фильтр по известному типу даты, если запрос его содержит | `mtime` не выдаётся за дату описанного события |

В metadata/entity/temporal отсутствие достоверных данных означает отсутствие соответствующего сигнала. Интерфейсы допускают будущее расширение на типизированные сущности и отношения, но их фиктивные результаты не входят в первую версию.

Raw source дополняет summary/topics и не теряется целиком после understanding. Для длинного извлечённого текста выбирается ограниченный набор фрагментов с покрытием разных частей/разделов, а не только начало. Для media без transcript используются реально доступные извлечённые признаки и understanding; система не заявляет, что исследовала отсутствующий transcript.

### 6.2. Structural Target Index — только для Crusher

Сохраняется существующая структурная интерпретация: настроенная root-нота ссылается на `#main`, `#main`/`#key` ссылаются на вложенные `#key`. Валидная опора достижима из root по этой структуре, имеет однозначный структурный путь и не совмещает конфликтующие роли `#main` и `#key`.

Обычные ссылки вне этой проекции не становятся структурными рёбрами. Недостижимая нота с нужным тегом не является опорой. Root не выбирается как обычное место. Ограничение старого greedy-алгоритма в восемь шагов снимается; построение проекции использует visited-set, ограничение числа узлов/рёбер и существующие лимиты базы.

Cycles/multiple parents исключают затронутые опоры из auto-placement, но не запрещают искать их текст в общем механизме. `pool` — отдельное явно разрешённое исключение, описанное в §8.

### 6.3. Состав PlacementProfile

Профиль хранит `anchor_ref`, структурный путь, роли, собственный текст опоры, дочерние structural topics, representative note/chunk refs, подтверждённые entity mentions, coverage, embeddings, source hashes и версию сборщика.

Правила принадлежности:

1. Связь ordinary note → разрешённый anchor даёт членство в соответствующей ветке; это не то же самое, что anchor → child structural node.
2. Вложенные структурные ветки могут давать родительскому профилю ограниченное представительство с явным указанием происхождения.
3. Произвольные связи между обычными заметками дают contextual evidence, но не создают транзитивное членство всех соседей.
4. Несколько прямых опор означают неоднозначное/множественное членство; одна заметка не считается независимым подтверждением несколько раз.
5. Выбор representative notes должен быть воспроизводимым и разнообразным. Количество заметок ветки не даёт ей неограниченного преимущества.

Профиль строится программно из наблюдаемого содержимого. Генерируемое LLM описание не обязательно. Одного усреднённого вектора большой ветки недостаточно: сохраняются representative chunks и объяснение совпадения.

Шаблоны, pool и содержимое, связанное только с pool, не формируют тематическое преимущество обычной ветки. Они остаются доступны общему поиску при соответствующем scope. Каталог `root/crusher` не исключается из поиска: созданные там содержательные заметки участвуют на общих основаниях после commit.

Участие ранее автоматически размещённой заметки отмечается provenance. Её текст полезен, но сам факт прежнего auto-placement не считается новым независимым доказательством правильности ветки. Признаки учитывают долю таких свидетельств и предотвращают самоподтверждение ошибочной классификации.

### 6.4. Актуальность и scheduling

Изменения текста, tags, ссылок, aliases, переименование, удаление и смена embedding model инвалидируют зависимые chunks/profiles. Профиль публикуется только как завершённая версия. Использованный набор имеет version manifest; старые и новые части одного профиля не смешиваются.

Все индексы производные и восстанавливаются из Vault. Их удаление не удаляет ноты, шаблон или настройки. Canonical Vault и конфигурация входят в backup; объёмные индексы восстанавливаются после restore согласно общему контракту.

Переиспользуется текущий `semantic.py`. Его линейный vector scan проверяется на representative corpus; новый поисковый сервер/ANN-хранилище не вводится без измеренной необходимости.

Текущее правило остановки фоновой индексации при любой незавершённой задаче Crusher должно быть заменено: foreground retrieval использует доступную согласованную генерацию, а индексатор получает bounded batches между тяжёлыми foreground-операциями. Ожидание полного READY не должно зависеть от завершения ожидающей задачи. Неполный индекс даёт явный degraded-режим, а не взаимное ожидание.

## 7. Fusion, ranking, confidence и Curator

### 7.1. Fusion и повторная оценка

Начальный вариант — Reciprocal Rank Fusion с `k=60`: сумма `1 / (k + rank)` по независимым спискам после identity dedup. RRF использует позиции, не требует приводить raw BM25/cosine к общей шкале. Одинаковые результаты одного канала или повторного прохода не дают повторный голос: для пары object/strategy сохраняется лучшая позиция и provenance всех совпадений.

Сначала объединяются сравнимые evidence-объекты. Для placement затем выполняется отдельная агрегация evidence к опорам. Нельзя складывать raw score заметки, relation и профиля как одинаковые величины или считать их готовым общим рейтингом мест.

Exact duplicates и пересекающиеся chunks одного источника сворачиваются с сохранением provenance. Похожие по смыслу, но разные источники/версии/противоречащие утверждения автоматически не удаляются.

Reranker учитывает lexical/semantic match, подтверждённые entity matches, metadata, проверенные пути и специфичность относительно запроса. Для Crusher дополнительно оцениваются профили опор. Hard constraints применяются до решения и не компенсируются высоким semantic score.

После Relation Expansion оценивается объединённый набор исходных и новых кандидатов; сохраняется лучшая найденная альтернатива в пределах лимитов. Второй проход сравнивает результаты с первым, не стирая хорошие альтернативы. Все стадии имеют стабильный tie-break и versioned configuration.

### 7.2. Confidence

Используются наблюдаемые признаки: score/gap, coverage индексов, количество различных подтверждающих источников, согласие каналов с учётом зависимости, однозначность сущностей, согласованность путей и свежесть данных.

Близость parent/child не трактуется механически как провал: политика учитывает несколько допустимых уровней конкретности. Единственный найденный кандидат сам по себе не означает уверенность. Curator self-score не входит как вероятность правильности.

Порог auto-placement калибруется на отдельной выборке. Для каждого degraded-набора каналов нужна собственная подтверждённая калибровка; без неё auto-placement запрещён, используется pool. Общий knowledge lookup при этом может вернуть полезные результаты с явной неполнотой.

До прохождения quality gate новая версия может выполняться в shadow-режиме. Установка произвольного постоянного `0.90` взамен прежнего model confidence не считается выполнением требования.

### 7.3. Curator

Инженерный default переключателя — `false`, до установки и квалификации локальной модели. Сам рабочий Curator входит в пакет: наличие одной галочки или mock-ответов не считается реализацией.

Curator вызывается только при `enabled && ready && refinement_may_help && budget_available`. Причины: неоднозначные названия, близкие конкурирующие варианты, слабое покрытие поисковыми формулировками или недостаточная graph evidence. Ошибка пути pool, corrupt index или запрещённый scope не исправляются вызовом модели.

Вход: исходная задача/subject, top evidence с opaque handles, короткий подтверждённый graph slice, признаки неопределённости и оставшиеся лимиты. Передача всей базы запрещена.

Выход — строго проверяемый `CuratorProposal`: дополнительные terms, существующие entity handles/alias hypotheses, graph hints, optional candidate hypotheses и `request_second_pass`. Предложенные новые сущности/связи остаются гипотезами до подтверждения поиском; неизвестные handles не считаются свидетельствами.

Curator не может менять principal, output path, eligibility, hard filters, budgets или число проходов; не исполняет tools, shell, сетевые запросы или запись. Источники и шаблон рассматриваются как данные, не инструкции расширить эти права.

На timeout, unavailable или invalid proposal используется уже полученный основной результат с явным outcome. Скрытого перехода к внешней модели нет. Остаточная неопределённость Crusher заканчивается pool.

Право на единственный вызов резервируется durable checkpoint до inference. Если процесс прерван и завершённого ответа нет, после restart слот считается использованным: применяется основной результат с `interrupted` outcome, без второго скрытого вызова. Завершённый Proposal переиспользуется только с теми же входными hash/version и повторно проверяется на актуальность.

Локальная модель и runner выбираются на этапе квалификации, закрепляются version/digest/license в lock-файлах и поставляются через существующий lifecycle. Самовольная загрузка модели во время запроса запрещена. Конкретный артефакт определяется измерением на целевом хосте, а не новым продуктовым согласованием. Не прошедшая лимиты модель не получает статус READY.

## 8. Политика Crusher, pool и безопасная запись

### 8.1. Выбор опоры

Crusher рассматривает evidence по всей разрешённой базе, агрегирует его к опорам Structural Target Index и сравнивает несколько полных вариантов. Последовательное необратимое сужение до одной ветки не используется.

В первом пакете выбирается **одна основная опора**. Автоматические дополнительные связи с произвольными найденными заметками не добавляются. Это ограничение Crusher, а не общего графа. В дальнейшем multi-anchor можно вводить отдельной версией политики.

Достаточное подтверждение и валидная опора дают `placed`. Неоднозначность, отсутствие подходящего места, исчерпание поискового бюджета или неквалифицированный degraded-режим дают `pooled`, если fallback пригоден. Невозможность извлечь/понять источник или сгенерировать корректное содержимое не маскируется записью пустой заметки в pool.

### 8.2. Резервная нота

`crusher.fallback_note` содержит реальный путь к Markdown-файлу, default `root/pool.md`. Нота должна однозначно разрешаться существующим механизмом внутренних ссылок. Для default-маршрута нужна реальная связь настроенной root-ноты → pool. При выборе другой резервной ноты допускается подтверждённый путь от root; наличие `#main`/`#key` у самой резервной ноты необязательно.

Pool не участвует в конкуренции тематических опор: он выбирается по fallback-правилу. Новая заметка ссылается на него точно так же, как на обычный anchor. При отсутствии/неоднозначности root или fallback, неподдерживаемом имени и исчезновении файла запись блокируется до исправления конфигурации. Непривязанная заметка или тихое возвращение к `Inbox/Crusher` недопустимы.

Если pool позже переименован подтверждённой canonical операцией, service setting обновляется с revision и audit, если идентичность установлена однозначно. Иначе Settings показывает, что путь требует исправления; одноимённый вновь появившийся файл не принимается за старый без проверки.

### 8.3. Запись

Порядок:

1. Проверить срок жизни job, policy/settings/template snapshots и готовность canonical Vault.
2. Проверить свежесть использованных evidence/profiles и актуальность структурного пути. При устаревании повторить оценку один раз в оставшемся бюджете; это не даёт дополнительных проходов Curator.
3. Если надёжное решение восстановить нельзя, проверить fallback из snapshot текущей попытки и его актуальную идентичность. Новая настройка из другой вкладки не подменяет его незаметно. Если и он непригоден, перейти в ожидание исправления конфигурации.
4. Сформировать итоговый Markdown из сохранённых generated fields и доверенных programmatic slots.
5. Под короткой canonical boundary повторно проверить необходимые версии/права, выделить уникальный basename и подтвердить отсутствие файла назначения.
6. Записать только новый файл в `root/crusher` через journal/CAS. Сохранить durable receipt и инициировать инкрементальную индексацию.

Папка не зависит от графового решения и не выбирается моделью. В первом пакете `root/crusher` — фиксированный контракт, в Settings показывается read-only. Новые варианты output directory требуют отдельного явного изменения этого контракта.

Внутренняя ссылка создаётся существующим canonical resolver/serializer. Default — `[[имя опорной ноты]]`; при неоднозначном basename используется поддерживаемое однозначное представление либо отказ с ясной причиной. Поддержка `@` сохраняется, но модель не выбирает произвольный reference syntax.

Ни provider, ни Curator не получают возможность задавать абсолютный путь, обходить path validation, перезаписывать файл или редактировать выбранную опорную ноту. Ссылки и системная provenance добавляются программно после валидации содержимого.

Crash до/после journal commit и повтор запроса не создают вторую заметку. Изменение файла самим Obsidian после успешного commit не является основанием восстановить прежние bytes при retry.

### 8.4. Ожидание конфигурации

Вводится явное `WAITING_CONFIGURATION` для ещё не завершённой задачи. Оно освобождает processing slot и показывает владельцу действие для продолжения. Гость видит только безопасное сообщение о задержке, без внутренних путей, template contents и найденных заметок.

Во время ожидания действует общий deadline job 60 минут. После него job становится failed; временные материалы хранятся не дольше существующих 24 часов и в пределах квоты. Owner может продолжить до истечения срока; после terminal failure — явно повторить с сохранённым материалом, пока он доступен. Успешная задача никогда не повторяет commit.

Продолжение после изменения настройки — явное owner-действие с новой attempt/config revision. Пригодные checkpoints извлечения/understanding переиспользуются; зависящие от изменённого шаблона/политики checkpoints пересчитываются. Подмена конфигурации выполняющейся задачи без такого перехода запрещена.

## 9. Шаблон Crusher

### 9.1. Владение и жизненный цикл

Шаблон — обычный UTF-8 `.md` в canonical Vault. Default `root/templates/example crusher.md`. Каталог участвует в обычном backup и доступен для редактирования в Obsidian. Mastermind не меняет глобальную конфигурацию Obsidian Templates и не затрагивает секреты/настройки сторонних плагинов.

Поле Settings позволяет выбрать другой Markdown-файл внутри Vault. Путь проверяется с теми же правилами, что canonical note paths: без traversal, escape через symlink и чтения `.obsidian`/служебных файлов как шаблона. Размер шаблона — не более 64 KiB.

На acceptance задачи фиксируются template path, hash, bytes, parser version, settings revision, timezone и timestamp. Изменение шаблона влияет на новые задачи; уже начатая использует свой snapshot. Удалённый до snapshot шаблон — ошибка конфигурации; удаление исходного файла после успешного snapshot не уничтожает snapshot выполняющейся задачи.

При повторном явном запуске можно выбрать текущий шаблон; изменение версии должно быть видно в attempt provenance. Сервис не создаёт новую пустую заметку до окончания генерации и проверок.

### 9.2. Поддерживаемый контракт подстановок

В первом пакете используется Markdown с небольшим явным набором placeholders. Это контракт renderer Mastermind; пользовательские расширения `crusher.*` не объявляются встроенными возможностями Obsidian. В Obsidian файл остаётся редактируемой заметкой-шаблоном.

| Placeholder | Источник значения | Правило |
| --- | --- | --- |
| `{{title}}` | Проверенное название результата | Plain text, экранирование Markdown по позиции |
| `{{date}}` | Зафиксированное время задачи и timezone | `YYYY-MM-DD`, одинаково при resume |
| `{{time}}` | То же | `HH:mm`, одинаково при resume |
| `{{crusher.summary}}` | Generated field `summary` | Короткая суть, без новых ресурсных ссылок |
| `{{crusher.body}}` | Generated field `body` | Основной материал; необходимые подразделы выбираются по источнику |
| `{{crusher.sources}}` | Проверенный source/provenance builder | Источник, без secret-bearing URL и локальных host paths |
| `{{crusher.links}}` | Итоговый PlacementDecision | Одна проверенная внутренняя ссылка |

`crusher.body` и `crusher.links` обязательны и встречаются ровно один раз. Остальные — опциональны, каждый не более одного раза. Placeholders находятся вне code fences и YAML frontmatter. Неизвестный placeholder, отсутствие обязательного slot или дублирование — ошибка проверки шаблона, не тихое удаление текста.

Литеральный Markdown и порядок разделов сохраняются. Модель получает bounded представление структуры шаблона и должна вернуть строго типизированные `title`, `summary`, `body`, а не переписывать весь template или придумывать новые slots. Пустые обязательные поля, неподдерживаемые ссылки/HTML/embeds и превышение output budget отклоняются существующим validator с необходимым расширением схемы.

Подстановка однопроходная: текст generated fields не интерпретируется как новый шаблон. Последовательность, похожая на placeholder внутри источника/ответа, не может повторно вставить системную ссылку или выполнить команду.

Безопасный статический YAML frontmatter шаблона допускается после отдельной проверки; поля, создаваемые моделью, туда не интерполируются. Структурные роли `#main`/`#key` и системные provenance markers шаблон не может выдавать новой Crusher-ноте. Произвольные внутренние ссылки вне `crusher.links` отклоняются с понятной ошибкой, чтобы шаблон не обходил placement policy. Сведения об источнике создаются только доверенным slot builder.

Шаблон не исполняет JavaScript, shell, Templater commands, произвольные include или вложенные шаблоны. Поддержка нового syntax добавляется versioned parser-изменением, а не эвристическим исполнением похожего текста.

### 9.3. Начальное содержимое example crusher.md

```markdown
# {{title}}

## Кратко

{{crusher.summary}}

## Основной материал

{{crusher.body}}

## Источник

{{crusher.sources}}

## Связи

{{crusher.links}}
```

Разделы внутри `crusher.body` адаптируются к содержанию. Отсутствующие факты не выдумываются ради заполнения структуры. Текст источника и формат template не дают модели права изменять pipeline instructions, выбирать путь или обходить validation.

## 10. Единая карточка Settings

Название: **`Obsidian & search`**. Одна `4x` Settings card по Part 01; отдельные карточки Obsidian и retrieval в этом пакете не создаются. Внутри — два логических подраздела, без отдельной навигационной вкладки.

| Элемент | Вид | Поведение |
| --- | --- | --- |
| `Crusher folder` | Read-only path | Показывает `root/crusher`; объясняет, что это физическое место файлов |
| `Fallback note` | Path input + выбор `.md` | Default `root/pool.md`; пояснение о связи в графе |
| `Crusher template` | Path input + выбор `.md` | Default `root/templates/example crusher.md`; рядом с Fallback note |
| `Enable Curator` | Checkbox | Сохраняет желаемое включение общего Curator |
| `Curator status` | Read-only state | Disabled / Ready / Unavailable / Error и безопасная причина |
| `Search index` | Read-only state | Ready / Indexing / Degraded / Unavailable, coverage и требуемое действие |
| `Apply` | Кнопка | Атомарно проверяет и сохраняет изменённые поля |

Выбор пути доступен только владельцу. Он не создаёт endpoint перечисления Vault для Shared/Crusher visitors. Поля и кнопки доступны с клавиатуры, длинные пути переносятся/прокручиваются внутри контрола без потери доступности, ошибки привязаны к полю.

Изменения формы — draft до Apply. Во время запроса повторное сохранение блокируется; неуспех сохраняет draft и прежнюю рабочую конфигурацию. Уведомления используют зелёный success и красный failure с текстом, системный accent применяется к focus/primary actions. Порядок карточки сохраняется существующим механизмом Settings.

Невалидный pool/template отклоняет изменение соответствующего поля; изменение только Curator не должно требовать повторного выбора уже настроенных путей. Включение при недоступной модели сохраняется как requested=true/effective=false с явным сообщением; это не зелёное подтверждение готовности модели. После восстановления готовности следующие задачи могут использовать Curator согласно snapshot.

Переключатель не заставляет текущую задачу менять ветку исполнения. Отключение отменяет использование для новых задач; явно выполняющийся ограниченный вызов завершается в пределах своего deadline. Административная остановка Worker остаётся отдельным действием.

Объединение этой карточки не отменяет обязательную отдельную `Wyverne Connection` для внешнего LLM по Part 10. Provider credentials и управление общими Adapters сюда не переносятся.

### 10.1. Конфигурационный API

Предлагаемый контракт отдельного owner resource:

```text
GET   /api/owner/context-indexing/settings
PATCH /api/owner/context-indexing/settings
POST  /api/owner/context-indexing/validate
```

Ответ содержит `revision`, `crusher.output_dir` (read-only), `crusher.fallback_note`, `crusher.template_path`, `retrieval.curator_enabled` и отдельный блок computed readiness. `crusher_root` сохраняет существующий источник конфигурации и возвращается read-only как контекст; второй независимый root-setting не создаётся.

PATCH содержит `expected_revision`, stable `operation_id` и только изменённые writable fields. Обязательны owner auth, CSRF и backend validation. Stale revision → `409 SETTINGS_CONFLICT` без частичного применения. Повтор того же operation_id с тем же payload возвращает прежний результат; другой payload с тем же ID отклоняется. Validate проверяет draft без записи и не запускает provider inference.

Stored configuration входит в authoritative backup. Computed readiness не становится сохранённой «истиной» и пересчитывается после restart/restore. В Bridge не появляется второй независимый источник этих настроек.

## 11. Интеграция в стадии Crusher

| Стадия | Новое поведение |
| --- | --- |
| Acceptance / QUEUED | Проверить конфигурацию, зафиксировать template/settings snapshots и policy version, зарезервировать storage |
| ACQUIRING / NORMALIZING / EXTRACTING | Сохранить существующий bounded intake, Worker isolation и verification; подготовить raw features |
| UNDERSTANDING | Внешняя модель через Wyvern формирует проверенные поля понимания источника |
| PLACING | Выполнить общий retrieval с Crusher policy, при необходимости Curator, получить placed/pooled |
| GENERATING | Передать понимание источника, разрешённые source excerpts и bounded структуру template; получить typed fields |
| VALIDATING | Проверить поля, template contract, размер и ссылки; собрать предварительный Markdown |
| COMMITTING | Повторно проверить версии/опору, окончательно заполнить trusted slots и атомарно записать в root/crusher |
| COMPLETED | Подтвердить durable receipt; новая заметка доступна в Vault |
| WAITING_CONFIGURATION | Владелец исправляет обязательный путь/конфигурацию; processing slot свободен |

Публичные страницы продолжают показывать только источник, прогресс, этап и безопасную ошибку. На Crusher не добавляются результат генерации, список evidence, внутренние пути или private placement diagnostics. Общий retrieval API в первом пакете — внутренний Python/service contract с проверками scope, не новый публичный маршрут.

## 12. Начальные лимиты и поведение при деградации

Лимиты применяются сервером; второй проход разделяет общий бюджет, а не получает новый неограниченный. Существующие пределы исходных файлов, extractor, очереди и всего job из итоговых требований сохраняются.

| Область | Инженерный default |
| --- | --- |
| Текст обычного поискового запроса | 16 KiB UTF-8; явно отклонить превышение |
| Raw source для query features | До 8 фрагментов по 512 embedding tokens; плюс bounded understanding, с отметкой неполноты |
| Результаты одного retrieval channel | До 50 evidence objects на проход |
| Первичная совокупность evidence | До 300 уникальных objects до fusion; до 100 после fusion |
| Graph traversal | До 2 hops; Relation Expansion — 1 hop, до 64 новых objects, общий union до 200 |
| Placement ranking | До 20 опор после агрегации; итог до 3 альтернатив для private diagnostics |
| Representative profile | До 12 различных нот, до 2 chunks на ноту; metadata сообщает полное число членов/coverage |
| Embedding execution | Существующий pinned model; batch ≤16, chunk ≤512 tokens |
| Curator context / output | До 6000 input tokens и 1000 output tokens; local token counting |
| Curator calls | Максимум 1 на query/job placement, включая resume с сохранённым outcome |
| Curator deadline | 45 s; timeout прекращает inference и освобождает ресурсы |
| Retrieval pass / всё placement | 15 s на проход; общий deadline 90 s, включая Curator и ограниченную revalidation |
| Foreground concurrency | Один Crusher job; общий retrieval admission — до 2 запросов, без неограниченной очереди |
| Template | ≤64 KiB UTF-8; snapshot входит в reservation job |
| Generated output | Существующий предел ≤8000 model tokens и итоговый max_note_bytes |
| Search trace | ≤64 KiB/query без raw body; 7 дней, максимум 10000 записей и 64 MiB суммарно |

Число членов профиля не ограничивается representative sample; лимит ограничивает материал представительства. При обрезании выдачи возвращается `truncated=true`; недосмотренные данные не считаются отсутствующими. Если runtime не успевает в лимиты, результат помечается degraded/insufficient и auto-placement без соответствующей калибровки не выполняется.

Исходные process limits сохраняются: Core 2 GiB, Runtime 3 GiB, Worker 2 GiB RAM/2 vCPU на целевом профиле 4 vCPU/8 GiB. Curator должен укладываться в Worker budget, при необходимости сериализуя тяжёлые операции и выгружая неиспользуемую модель. Нельзя незаметно добавить безлимитный inference process. Невозможность квалифицировать выбранный artifact означает выбор другого artifact/оптимизацию, а не ложный READY.

Недоступный vector index, partial profiles и stale generation отражаются в readiness и trace. Деградация поиска не делает здоровый Core «готовым ко всем функциям». Restart/restore и missing model проверяются отдельно.

## 13. Privacy, audit и provenance

Внешние understanding/generation используют Wyvern с клиентской идентичностью и разрешённым функциональным Adapter. Ключи provider остаются в Volt через Kernel в зоне ответственности gateway; Mastermind не извлекает их в новые настройки или Curator. Недоступный Adapter не заменяется скрытым direct-provider fallback.

В новой версии поиск по Vault, профили, paths и выбор anchor локальны. Во внешний generation передаются source/understanding и необходимая структура выбранного владельцем template; найденные заметки и профили туда автоматически не добавляются. Template literals тоже считаются Vault-derived context. Прежние верхние бюджеты ≤12000 unique / ≤24000 transmitted Vault tokens и ≤32000 source-input tokens/job не увеличиваются. Бюджет проверяется до передачи; удалённый countTokens также является передачей и не должен обходить лимит.

Содержимое `.obsidian`, секреты сторонних плагинов и credentials не индексируются для этого механизма и не передаются через него. Existing Shared sanitization и запреты доступа к другим ресурсам сохраняются.

Private trace содержит версии QueryPlan/политики/калибровки/model/index/profile/template, hashes, channel coverage, числа кандидатов, ссылки на evidence, reason codes, curator outcome и timings. Raw source, query text, заметки и полные prompts не дублируются в обычные logs/audit. Снимки для resume находятся в защищённом job storage с квотами и сроком жизни исходной задачи.

Trace доступен только владельцу/авторизованному обслуживанию; public progress не раскрывает его поля. Удаление/изменение evidence делает trace историческим: ссылка с устаревшим hash не выдаётся за текущий факт. После retention полного trace остаётся только минимальная commit provenance, необходимая для существующего receipt/идемпотентности.

Audit фиксирует применение настроек, конфликты revision, перестроение индексов, изменение готовности Curator, outcome placement и commit без содержимого заметок. Действуют общие redaction и retention из Part 02.

## 14. Миграция и совместимость

### 14.1. Подготовка defaults

Миграция идемпотентна, проходит через canonical coordinator и создаёт только отсутствующие необходимые объекты:

1. Каталоги `root/crusher` и `root/templates`.
2. `root/templates/example crusher.md` с содержимым §9.3, если такого файла нет. Существующий файл никогда не заменяется эталоном; сначала проверяется его пригодность.
3. Резервная нота: сначала проверить настроенный fallback и уже существующую однозначную ноту `pool`. Не создавать дубликат basename. Если её нет — создать `root/pool.md` без `#main`/`#key`.
4. Подтвердить связь root → pool. Для нового default-pool добавить её в существующую root-ноту один раз через CAS, сохранив остальной текст. Это отдельная bootstrap-операция, а не редактирование родителя каждым Crusher job.
5. Сохранить schema/config revision, выбранные пути и `curator_enabled=false`, если настройки ещё нет. Существующее явное значение не сбрасывать.

Если root не настроен/не существует, pool неоднозначен или существующий шаблон не проходит validation, миграция не угадывает структуру и не портит файлы. В Settings появляется конкретное действие для завершения настройки; уже работающие несвязанные функции сервиса остаются доступны.

Defaults предназначены для будущего внедрения. Создание этого документа само по себе не создаёт перечисленные файлы в рабочем Vault.

### 14.2. Переход с текущего placement

Включение новой версии выполняется после приёмки пакета. На cutover временно приостанавливается acceptance новых Crusher jobs; активные старые jobs завершаются в пределах deadline либо переводятся в явное восстанавливаемое состояние. После активации все новые commits Crusher используют `root/crusher`, template и новую policy.

Ещё не начатые legacy jobs получают новую конфигурацию при явной миграции attempt. Пригодные source/understanding checkpoints можно сохранить. Старое placement/generation без требуемой template/config version не принимается как готовый результат новой версии.

Существующие заметки в старых папках, включая `Inbox/Crusher`, автоматически не перемещаются и не перелинковываются. Они остаются обычными доступными поиску заметками. Их миграция не нужна для корректности нового механизма.

Изменения State schema имеют migration version. Rebuild новых derived tables не стирает authoritative settings, canonical note contents, receipts или provenance. Старые и новые index generations не выдаются за взаимозаменяемые.

### 14.3. Rollback

Rollback восстанавливает совместимые binaries/config interpretation по существующему lifecycle. Он не удаляет уже созданные заметки, pool или изменённый владельцем template и не откатывает чужие редактирования Vault.

Legacy Crusher, сохраняющий файлы рядом с anchor, после rollback не должен незаметно возобновить acceptance. Если прежняя версия не понимает новый output/template contract, Crusher остаётся остановлен до восстановления совместимой версии; Vault/Shared и другие пригодные функции могут продолжать работать.

## 15. Карта изменений в реализации

Названия новых модулей ориентировочные; границы ответственности обязательны. Текущее дерево проверено при подготовке спецификации и может измениться к началу работ.

| Область | Требуемое изменение |

| Новая Crusher policy | Eligibility, evidence→target aggregation, calibrated placement и pool fallback |

## 16. Оценка качества до и после изменений

### 16.1. Набор данных

Подготовить до настройки нового ранжирования не менее 300 проверяемых placement cases, включая не менее 100 в отложенной test-части. Это инженерный минимум для первой приёмки, не доказательство универсальной точности.

Каждый case задаёт исходный материал, snapshot графа, множество допустимых опор либо `must_pool`, и объяснение разметки. Нужны разные ветки, уровни вложенности, короткие/длинные источники, смешанные темы, русский/английский текст, омонимы, недостижимые/циклические опоры, отсутствие данных и новые темы.

Train/development, calibration и test разделяются по группам связанных источников/дубликатов. Проверяемая нота, её дубликаты и вклад в profile не присутствуют в поисковом corpus этого case. Нельзя оценивать placement заметки по профилю, который уже «знает» её правильное размещение.

Отдельный набор knowledge lookup проверяет поиск обычных нот и связей без structural eligibility. Размеченная ожидаемая связь подтверждается реальными edges/evidence; будущий поиск корреляций не объявляется реализованным этой проверкой.

### 16.2. Метрики и начальный quality gate

Измерять candidate Recall@K, placement top-1/top-3, auto-placement precision/coverage, ошибочный auto-placement на `must_pool`, долю pool, curator invocation/refinement rate, p50/p95 latency, RSS и размер индексов.

Начальные release gates:

- Ни одного нарушения output directory, eligibility, scope, ссылочного направления или безопасного commit в функциональной матрице.
- На held-out placement set наблюдаемая auto-placement precision ≥98%; не менее 50 автоматических решений для содержательного отчёта. Иначе выборка/coverage недостаточна для приёмки.
- Ноль auto-placement на размеченных `must_pool` в held-out set.
- Coverage при сопоставимой precision не хуже baseline; результаты и интервалы неопределённости приводятся явно. Исходный baseline измеряется до настройки.
- Candidate recall и ошибки разбираются отдельно: Curator не маскирует систематическую потерю правильной ветки на retrieval.
- Curator-on не ухудшает допустимую precision. Для рекомендации включать его нужна подтверждённая польза на заранее выделенной группе сложных случаев. Если прироста нет, функционально проверенный Curator остаётся доступным с default off, а отсутствие измеренной пользы явно отражается в отчёте.

Числа выше — критерии для реализации, не результаты уже выполненного эксперимента. Небольшая выборка не позволяет называть score статистически надёжной вероятностью для всей базы.

Сравнить baseline и варианты без Curator, с profiles, с global vector, с graph expansion и с Curator на одной зафиксированной выборке. Изменение порогов после просмотра test-ответов требует нового held-out set, а не повторной отчётности по прежнему.

Placement dataset оценивается на зафиксированных SourceFeatures и графовых snapshots; он не требует повторять acquisition/understanding/generation для каждого варианта. Существующие реальные ответы legacy placement можно воспроизводить из защищённых fixtures для тех же входов. Результаты mock-провайдера обозначаются как simulation и не подменяют измерение качества реального legacy baseline. Сравнение coverage допускается только на сопоставимой части с достоверным baseline; её размер и происхождение ответов указываются в отчёте.

## 17. Этапы единого пакета

Этапы — внутренние контрольные точки, а не обязательные отдельные пользовательские релизы. Для каждой сохраняются входные условия, выходные артефакты и PASS/FAIL evidence.

| Этап | Вход | Выход | Выходная проверка |
| --- | --- | --- | --- |

Сквозной стенд использует локальные копии причастных сервисов: Core, Worker, Obsidian Runtime/Bridge, Kernel/Volt, Wyvern и, для соответствующих сценариев, Saturn/Neptune. Их exact versions/digests фиксируются в отчёте. Готовность чужого сервиса не объявляется по наличию контейнера.

Минимальные end-to-end источники: небольшой текстовый файл, публичная тестовая web-страница, небольшой media fixture и разрешённый owner Saturn resource. Каждый проверяется до фактического файла в Vault, его template sections и правильной внутренней ссылки. Проверяется guest intake без доступа к результату. Объём synthetic fixtures — несколько MiB; проверки граничных размеров используют контролируемые metadata/stream/fault cases без обязательной передачи 8 GiB.

Реальный внешний API проверяется отдельно на нечувствительных fixtures через настроенный Wyvern. Наличие fixture-provider тестов не подтверждает real-provider readiness; отсутствие доступной интеграции отмечается как непрошедший соответствующий gate, а не PASS. Новые ключи не запрашиваются и не копируются в документацию/артефакты; используется установленный секретный контур.

Нет обязательного восьмичасового soak. Регрессия состоит из ограниченных сценариев, циклов restart/retry и измеряемых deadline/resource checks. Ошибочные тестовые заметки удаляются только по точному пути и ожидаемому hash; рабочие заметки и пользовательские шаблоны не служат расходными fixtures.

## 19. Граница готовности и отложенное расширение

Пакет готов, когда реализованы D01–D16, пройдены CP0–CP7 и T01–T24, опубликованы реальные результаты quality/resource checks, а документация и operator UI отражают фактическое поведение. Недоступная обязательная интеграция, рабочий только на mocks Curator или неподтверждённая миграция остаются незавершённой работой.

Допускается штатно выключенный пользователем Curator: это режим готовой функции. Он отличается от отсутствующей реализации или неквалифицированной модели. Включение не должно требовать изменения архитектуры, ручного патча кода или передачи ключа в форму Settings.

В этом пакете не реализуются: полноценный поиск корреляций/каузальных выводов, универсальная онтология сущностей, автоматическое создание semantic relations, multi-step autonomous agents, remote Curator fallback, multi-anchor mutation, semantic dedup с удалением фактов и исполнение сторонних template plugins. Для будущих потребителей остаются общие interfaces, unrestricted-by-tags retrieval и versioned evidence contracts.

Открытых продуктовых развилок, блокирующих начало реализации, нет. Подбор pinned локальной модели, измерение ranking/calibration параметров и квалификация версий зависимостей — предусмотренные инженерные работы CP0–CP6. Их результаты должны быть зафиксированы; они не дают права менять согласованные направления ссылок, output folder, границы общего поиска или объединённую карточку Settings.
